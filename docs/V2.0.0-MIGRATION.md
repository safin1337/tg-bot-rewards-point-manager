# SoulShop V2.0.0 migration runbook

This runbook is intentionally manual. Do not deploy, modify Telegram, or apply
remote D1 migrations from an automated coding session.

## What changes

- `0004_mutation_receipts_and_leaderboards.sql` extends persisted workflow
  operations, creates receipts/leaderboard/reset structures, backfills every
  existing transaction receipt, and builds current/recent weekly and monthly
  aggregates.
- `0005_verify_backfill_and_prune_history.sql` checks receipt and applicable
  aggregate consistency, then prunes detailed rows beyond the newest 40 per
  customer. A failed check aborts that migration before deletion.

Previously deployed migrations `0001` through `0003` are unchanged.

## 1. Validate locally

From PowerShell:

```powershell
Set-Location "D:\TG_Bot-Project"
$env:XDG_CONFIG_HOME = "$PWD\.wrangler\config"
$env:WRANGLER_LOG_PATH = "$PWD\.wrangler\logs\wrangler.log"

npm.cmd run db:migrate:local
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run test:run
npm.cmd run build
```

Confirm foreign keys on the local database:

```powershell
npx.cmd wrangler d1 execute soulshop-rewards-db `
  --local `
  --command="PRAGMA foreign_key_check;"
```

An empty result is required.

## 2. Take a protected production backup

Choose a private ignored path and verify the target database before running:

```powershell
New-Item -ItemType Directory -Force "backups" | Out-Null
npx.cmd wrangler d1 export soulshop-rewards-db `
  --remote `
  --output="backups/soulshop-pre-v2-YYYY-MM-DD.sql"
```

The backup contains customer phone numbers and transaction notes. Keep it out
of Git and store it under appropriate access controls. Verify that the file is
nonempty before continuing.

## 3. Review pre-migration counts

Run read-only queries manually against the intended remote database:

```powershell
npx.cmd wrangler d1 execute soulshop-rewards-db `
  --remote `
  --command="SELECT COUNT(*) AS customers FROM customers; SELECT COUNT(*) AS transactions FROM transactions;"
```

Record the counts privately; do not paste customer rows into logs or tickets.

## 4. Apply versioned migrations

Only after backup and review:

```powershell
npm.cmd run db:migrate:remote
```

Wrangler applies `0004` before `0005`. Do not execute or mark migration files
manually. `0005` cannot prune if the receipt or applicable aggregate backfill
verification fails.

## 5. Verify before deploying the Worker

```powershell
npx.cmd wrangler d1 execute soulshop-rewards-db `
  --remote `
  --command="PRAGMA foreign_key_check; SELECT COUNT(*) AS missing_receipts FROM transactions t LEFT JOIN mutation_receipts r ON r.telegram_update_id = t.telegram_update_id WHERE r.telegram_update_id IS NULL; SELECT customer_id, COUNT(*) AS retained FROM transactions GROUP BY customer_id HAVING retained > 40;"
```

Required results:

- no foreign-key violations;
- `missing_receipts = 0`;
- no customer with more than 40 detailed transactions.

Also compare customer count and authoritative balance totals with the private
pre-migration record. Pruning must not change `customers.point_balance_units`
or `customers.rounded_reward_bdt`.

## 6. Deploy and Telegram configuration

Deploy the V2.0.0 Worker only after database verification. Webhook registration
and command registration remain separate manual operations. This repository's
tests and dry-run build never perform them.

## Restore considerations

Pruned detail is intentionally irreversible in the live V2 database. Restoring
old detail requires the protected pre-migration backup and a separately tested
recovery database. Do not import a pre-V2 backup over a running V2 database:
it lacks receipt and leaderboard structures and may reintroduce more than 40
detailed rows per customer.

Test restoration into a separate D1 database, apply the V2 migrations there,
run all consistency queries, and only then plan any production recovery.
