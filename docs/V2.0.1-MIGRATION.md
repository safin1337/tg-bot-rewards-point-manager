# SoulShop V2.0.1 migration runbook

Migration `0006_bounded_operational_storage.sql` upgrades the current V2.0.0
schema and is also applied during a fresh installation. It does not recalculate
customer balances or leaderboard aggregates from retained history.

## What the migration changes

- Adds and backfills `customers.latest_mutation_telegram_update_id` from
  completed mutation receipts without changing any balance or reward value.
- Removes completed mutation receipts whose corresponding detailed transaction
  is no longer retained, plus abandoned committed `PROCESSING` rows. A genuine
  active mutation claim is uncommitted inside its atomic D1 batch and is not
  visible to migration cleanup.
- Adds the transaction-to-completed-receipt paired-delete trigger and retention
  indexes.
- Bounds leaderboard reset receipts and eligible non-active processed updates
  to the intersection of the clamped two-UTC-calendar-month window and the
  deterministic latest 40.
- Preserves genuinely active five-minute processed-update leases.
- Fails if `PRAGMA foreign_key_check` reports a violation.

The exact cutoff and full retention matrix are documented in
[DATABASE.md](DATABASE.md).

## Required pre-production sequence

1. Stop or otherwise quiesce production mutations for the migration window.
2. Take a protected D1 backup containing schema and data. It includes private
   phone numbers and notes and must remain outside Git.
3. Record customer count, total point units, total rounded reward BDT,
   leaderboard generations/totals, transaction counts by customer, and receipt
   counts.
4. Apply the migration to an isolated restored copy and run all verification
   queries below.
5. Apply migration `0006` to production only after explicit approval.
6. Deploy the matching V2.0.1 Worker only after migration verification.

This repository preparation performed none of steps 1, 2, 5, or 6 against
production.

## Verification queries

```sql
PRAGMA foreign_key_check;

SELECT customer_id, COUNT(*) AS retained
FROM transactions
GROUP BY customer_id
HAVING retained > 40;

SELECT customer_id, COUNT(*) AS retained
FROM mutation_receipts
WHERE status = 'COMPLETED'
GROUP BY customer_id
HAVING retained > 40;

SELECT receipt.telegram_update_id
FROM mutation_receipts AS receipt
LEFT JOIN transactions AS transaction_row
  ON transaction_row.telegram_update_id = receipt.telegram_update_id
 AND transaction_row.customer_id = receipt.customer_id
 AND transaction_row.transaction_type = receipt.mutation_type
WHERE receipt.status = 'COMPLETED'
  AND transaction_row.id IS NULL;

SELECT COUNT(*) AS reset_receipts FROM leaderboard_reset_receipts;

SELECT status, COUNT(*) AS processed_updates
FROM processed_updates
GROUP BY status;
```

The first three queries must return no rows. Reset receipts may not exceed 40.
Eligible non-active processed updates may not exceed 40; genuinely active
leases can temporarily make the table total higher.

Compare the recorded pre/post totals for customers, point balances, rounded
reward BDT, leaderboard generations, and aggregate earned units. They must be
identical. Only obsolete operational receipts may decrease.

## Rollback considerations

Do not attempt an ad-hoc reverse SQL migration. The migration removes obsolete
receipts, and reversing the added high-water column or trigger cannot restore
those rows. If verification fails before Worker deployment, restore the entire
database from the protected pre-migration backup into an isolated database,
verify it, then follow Cloudflare's current D1 restore procedure for the
intended target. Never overwrite a live database without explicit approval and
a fresh recovery point.

The V2.0.1 Worker expects the high-water column and retention trigger. Do not
deploy it against an unmigrated database, and do not run the older V2.0.0
Worker after operational receipt pruning without a reviewed rollback plan.
