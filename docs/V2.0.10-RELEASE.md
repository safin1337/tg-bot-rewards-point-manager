# V2.0.10 release guide

V2.0.10 adds strict two-line `/quickbuy`, a direct `/testaccounts` command, a
smaller visible Telegram command list, and safe callback/state round-trip
optimizations. It adds no D1 migration and uses the V2.0.9 schema with
migrations through `0009_dashboard_and_test_accounts.sql` applied.

No production action in this guide is automated. Run each external command
only from the reviewed V2.0.10 commit and with the intended account selected.

## 1. Local validation

From PowerShell in the repository root:

```powershell
npm.cmd ci
npm.cmd run db:migrate:local
npm.cmd run check
git diff --check
git status --short
```

Review the complete source, tests, command JSON, documentation, and package
version diff. The build inside `check` is a Wrangler dry run and does not
deploy.

## 2. Production prerequisites

Before deployment:

1. Confirm the deployed database already has migration 0009.
2. Pause administrator purchases and other mutations for the short deployment
   window.
3. Take and protect a current remote D1 export even though this release has no
   migration.
4. Record aggregate customer, point-unit, transaction, and receipt counts
   without exposing customer identifiers.
5. Confirm no unfinished purchase confirmation or Quick Buy operation should
   be carried across a rollback test.

Example verification commands:

```powershell
npx.cmd wrangler whoami
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
New-Item -ItemType Directory -Force "backups" | Out-Null
npx.cmd wrangler d1 export soulshop-rewards-db `
  --remote `
  --output="backups/soulshop-pre-v2.0.10-YYYY-MM-DD.sql"
```

Backups contain private customer data and must remain ignored and protected.

## 3. Deploy before changing Telegram commands

Deploy the reviewed Worker first:

```powershell
npm.cmd run deploy
```

Verify the returned Worker URL and `GET /health`. Do not register the new
visible commands until the deployed Worker can route `/quickbuy` and
`/testaccounts`; otherwise Telegram may advertise commands the live Worker
does not understand.

## 4. Acceptance

Using only the authorized administrator, verify:

- `/quickbuy` asks for a WhatsApp number on the first line and a positive
  whole-number BDT amount on the second line.
- One exact existing-phone purchase uses that customer, assigns the expected
  integer point units once, updates the applicable leaderboard, and displays
  the normal final purchase receipt without a confirmation panel.
- One disposable new phone creates a normal phone-only customer and records
  the purchase. Confirm no username-only account was inferred or merged.
- Decimal/decorated amounts, suffixes, usernames, malformed phones, blank
  lines, missing lines, and extra lines return the approved concise error and
  create no customer, transaction, receipt, points, or leaderboard row.
- `/restart` returns an active Quick Buy to its own two-line input step and
  `/cancel` exits without mutation.
- `/testaccounts` opens the existing tokenized test-account workflow.
- Ordinary dashboard, More Tools, search, Back, pagination, confirmation,
  redemption, export, and leaderboard actions still enforce authorization,
  tokens, expected values, idempotency, and edit/send fallback behavior.
- Customer balances, aggregate point units, transaction count, and receipt
  count changed only by the deliberate acceptance purchases.

Do not test a duplicate update against production by fabricating Telegram
updates. That behavior is covered by the local Worker test suite.

## 5. Register the compact visible command list

Only after the new Worker passes acceptance:

```powershell
$env:BOT_TOKEN = "YOUR_BOT_TOKEN_IN_THIS_PROCESS_ONLY"
npm.cmd run telegram:set-commands
Remove-Item Env:BOT_TOKEN
```

The visible list becomes `/start`, `/purchase`, `/quickbuy`, `/redeem`,
`/testaccounts`, `/tools`, `/restart`, and `/cancel`. `/help`, `/export`,
`/addpoints`, `/addcustomer`, `/history`, `/leaderboard`, `/balance`, and
`/managecustomer` remain manually routable and documented in `/help` and the
README.

## 6. Tag only after production acceptance

```powershell
git tag -a v2.0.10 -m "Release V2.0.10"
git push origin v2.0.10
```

Do not tag merely because local checks passed.

## 7. Rollback

V2.0.10 has no schema rollback. Before deploying V2.0.9, cancel or clear an
active `AWAIT_QUICK_PURCHASE` state because the older Worker does not recognize
that step. Then deploy the reviewed V2.0.9 Worker and re-register its intended
command list if necessary.

Do not delete or rewrite customers, balances, transactions, receipts,
leaderboards, or migration records. Preserve the backup and investigate any
unexpected result before further production changes.

## Release-state note

Preparing this release does not apply a remote migration, deploy a Worker,
register Telegram commands, change a webhook or secret, create a commit, push,
or tag. Every external step above remains manual.
