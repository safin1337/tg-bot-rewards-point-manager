# SoulShop V2.0.2 migration hotfix runbook

Migration `0006_bounded_operational_storage.sql` upgrades the current V2.0.0
production schema and is also applied during a fresh installation. It does not
recalculate customer balances or leaderboard aggregates from retained history.
Customers remain unbounded.

## Why V2.0.2 exists

The V2.0.1 form of migration `0006` contained a compound SQLite
`CREATE TRIGGER ... BEGIN ... END` statement. Wrangler submitted the complete
migration through the remote D1 query endpoint, which rejected that form with
`incomplete input: SQLITE_ERROR`. Wrangler rolled back the migration, and
production verification confirmed that `0006` remained pending, the customer
high-water column was absent, and the trigger was absent.

Because `0006` was never applied to production, V2.0.2 corrects that same
unapplied migration rather than adding a later migration that could never be
reached. The corrected migration removes only the compound trigger. Normal bot
mutations already delete old transactions and their corresponding completed
receipts as adjacent statements inside the same atomic D1 batch.

## Retention target preserved

- `customers` remains unbounded and authoritative for point balances.
- `transactions` retains the newest 40 rows per customer across `PURCHASE`,
  `MANUAL_ADD`, and `REDEEM` combined.
- Completed `mutation_receipts` correspond to those retained newest 40 rows.
- The per-customer mutation update-ID high-water mark rejects delayed updates
  after their detailed transaction and completed receipt are pruned.
- Leaderboard reset receipts and eligible non-active processed updates remain
  bounded to both the latest 40 overall and the clamped two-UTC-month window.
- Genuine active five-minute processed-update leases remain protected.
- Leaderboard periods and aggregates retain the current/previous-month and
  current/two-previous-week policy.

Direct manual deletion from `transactions` is unsupported unless the matching
completed `mutation_receipts` are deleted in the same reviewed D1 batch. Normal
Worker mutations always perform both pruning operations atomically.

## Required pre-production sequence

1. Confirm the release commit and tag are V2.0.2 and the working tree is clean.
2. Stop or otherwise quiesce production mutations for the migration window.
3. Take a protected D1 export containing schema and data outside Git and record
   the current D1 Time Travel bookmark.
4. Record customer count, total point units, total rounded reward BDT,
   leaderboard generations/totals, transaction counts by customer, and receipt
   counts.
5. Confirm `wrangler d1 migrations list soulshop-rewards-db --remote` reports
   only `0006_bounded_operational_storage.sql`.
6. Apply corrected migration `0006` to production only after explicit approval.
7. Run every verification query below and compare pre/post authoritative totals.
8. Deploy the matching V2.0.2 Worker only after migration verification.
9. Restore the Telegram webhook and perform administrator-only acceptance tests.

This repository preparation performed none of steps 2, 3, 6, 8, or 9 against
production.

## Verification queries

```sql
PRAGMA foreign_key_check;

SELECT customer_id, COUNT(*) AS retained
FROM transactions
GROUP BY customer_id
HAVING retained > 40;

SELECT customer_id, COUNT(*) AS retained
FROM mutation_receipts
WHERE status = 'COMPLETED'
GROUP BY customer_id
HAVING retained > 40;

SELECT receipt.telegram_update_id
FROM mutation_receipts AS receipt
LEFT JOIN transactions AS transaction_row
  ON transaction_row.telegram_update_id = receipt.telegram_update_id
 AND transaction_row.customer_id = receipt.customer_id
 AND transaction_row.transaction_type = receipt.mutation_type
WHERE receipt.status = 'COMPLETED'
  AND transaction_row.id IS NULL;

SELECT COUNT(*) AS reset_receipts FROM leaderboard_reset_receipts;

SELECT status, COUNT(*) AS processed_updates
FROM processed_updates
GROUP BY status;
```

The first three queries must return no rows. Reset receipts may not exceed 40.
Eligible non-active processed updates may not exceed 40; genuinely active
leases can temporarily make the table total higher.

Customer count, total point balances, total rounded reward BDT, leaderboard
generations, and aggregate earned units must be identical before and after the
migration. Only obsolete operational receipts may decrease.

After verification, confirm that remote migration listing reports no unapplied
migrations and that the `latest_mutation_telegram_update_id` customer column
exists. The removed V2.0.1 trigger must remain absent.

## Rollback considerations

Do not attempt an ad-hoc reverse SQL migration. Migration `0006` removes
obsolete operational receipts, and removing the added high-water column cannot
restore them. If verification fails before Worker deployment, keep the webhook
paused and follow Cloudflare's current D1 restore procedure using the protected
pre-migration recovery point. Never overwrite a live database without explicit
approval and a fresh recovery point.

The V2.0.2 Worker expects the high-water column and corrected retention policy.
Do not deploy it against an unmigrated database, and do not run the older
V2.0.0 Worker after operational receipt pruning without a reviewed rollback
plan.
