# V2.0.4 release runbook

V2.0.4 makes the Telegram loyalty manager public-friendly and configurable.
SoulShop remains the attributed default brand. Runtime branding, taglines,
purchase earning policy, redemption policy, help text, and CSV prefix now
derive from `src/config/app-config.ts`. The new default earning policy is BDT 50
= 1 point; redemption remains 4 points = BDT 1.

This release contains no D1 migration or data rewrite. Existing balances,
transactions, reward snapshots, mutation receipts, history, and leaderboard
totals remain unchanged. Only purchases confirmed under the new Worker use the
new earning rate. Pending confirmations calculated under another policy are
rejected without mutation and must restart.

## 1. Inspect the current branch and worktree

The implementation was prepared as uncommitted work on `main`. Inspect it:

```powershell
git status -sb
git branch --show-current
```

`## main...origin/main` with no file lines means a clean worktree. Modified and
new files appear beneath that branch line. Review every listed file before
creating the release branch.

## 2. Create the release branch with the current work

Do not pull while the worktree contains uncommitted changes. Create the branch;
Git safely carries the uncommitted files with it:

```powershell
git switch -c release/v2.0.4
git status -sb
```

## 3. Review the implementation

```powershell
git diff --check
git diff --stat
git diff
```

- `git diff --check` detects whitespace errors and conflict markers.
- `git diff --stat` shows the scope by file.
- `git diff` shows the full unstaged implementation.

Confirm no migration was created or modified and no unrelated change is
present.

## 5. Commit

```powershell
git commit -m "feat(v2.0.4): add public customization configuration"
git status -sb
git log -1 --oneline
```

The worktree should be clean after the commit.

## 6. Push only the release branch

```powershell
git push -u origin release/v2.0.4
```

This publishes the release branch and does not modify `main`.

## 7. Create and review the GitHub pull request

1. Open the repository on GitHub.
2. Select `release/v2.0.4`.
3. Click **Compare & pull request**.
4. Set base to `main` and compare to `release/v2.0.4`.
5. Use the title `Release v2.0.4 — public customization configuration`.
6. Summarize the public README, central branding/taglines, configurable earning
   policy, BDT 50 = 1 point default, unchanged redemption policy, no D1
   migration, stale-confirmation protection, and full validation result.
7. Review **Files changed**, especially `app-config.ts`, reward arithmetic, and
   confirmation handling.
8. Wait for every automated check.
9. Merge only after review succeeds, using the repository's normal merge
   strategy.

Creating this runbook does not create the pull request.

## 8. Synchronize local `main` after the GitHub merge

```powershell
git switch main
git pull --ff-only origin main
git status -sb
git log -1 --oneline
```

`--ff-only` prevents an accidental local merge commit.

## 9. Revalidate the merged commit

```powershell
npm ci
npm run db:migrate:local
npm run check
git status -sb
```

`db:migrate:local` uses only local D1 state. V2.0.4 adds no migration, so no
remote D1 migration command is needed. The worktree must be clean before
deployment.

## 10. Deploy with a Wrangler version message

Only after the pull request is merged and step 9 passes, run:

```powershell
npm run deploy -- --message "V2.0.4: add public customization and configurable reward policy"
```

The double dash passes `--message` through npm to Wrangler. This is a production
operation and is intentionally manual.

## 11. Verify Worker health

```powershell
Invoke-RestMethod "https://soulshop-rewards.<YOUR-SUBDOMAIN>.workers.dev/health"
```

Substitute the real `workers.dev` subdomain or custom Worker URL. Expected:

```text
status
------
ok
```

## 12. Inspect the existing webhook without changing it

```powershell
$env:BOT_TOKEN = "YOUR_BOT_TOKEN"
npm run telegram:webhook-info
Remove-Item Env:BOT_TOKEN
```

This reads webhook status only. Do not register it again when the Worker URL and
webhook secret are unchanged. Never paste a real token into a tracked file.

## 13. Live Telegram smoke test

Using only the configured administrator:

1. `/start` shows the default SoulShop branding.
2. The heading is `SoulShop Rewards Point System`.
3. Closing taglines include `Best Wishes from SoulShop`.
4. `/help` says every BDT 50 earns 1 point.
5. A BDT 50 purchase earns 1.00 point.
6. A BDT 500 purchase earns 10.00 points.
7. The prior customer balance is unchanged before that purchase.
8. Reward value remains based on 4 points = BDT 1.
9. Manual additions remain correct.
10. Redemptions remain correct and never say `Congratulations` on success.
11. Balance messages retain their required labels.
12. History remains newest-first and uses exact stored point behavior.
13. CSV exports retain exact four-decimal values and safe filenames.
14. Weekly and monthly leaderboards receive the newly earned point units.
15. History omits all three closing taglines.
16. Purchase, manual-add, redemption, and balance preserve their required
    closing lines.
17. An unauthorized Telegram user remains blocked.

If a real stale confirmation exists from the previous Worker, confirm it only
when operationally safe: it must display the policy-changed message, make no
database change, and require restart.

## 14. Tag only after successful production verification

From the verified `main` commit:

```powershell
git status -sb
git tag -a v2.0.4 -m "Telegram Bot: Loyalty Rewards Point Manager v2.0.4"
git push origin v2.0.4
```

Never move or reuse the tag. It must identify the exact code successfully
deployed. A GitHub Release may then be created from `v2.0.4` using the changelog
entry as release notes.

## 15. Optional branch cleanup

Only after confirming the pull request is merged and `main` contains the
commit:

```powershell
git branch -d release/v2.0.4
git push origin --delete release/v2.0.4
```

Branch deletion is optional.

## 16. Rollback

Inspect available Worker versions:

```powershell
npx wrangler versions list
```

If rollback is necessary:

```powershell
npx wrangler rollback --message "Rollback v2.0.4 public customization deployment"
```

Rollback changes the active Worker version and does not change the local Git
worktree. No D1 rollback is needed because V2.0.4 has no database migration.
After rollback, repeat the health, webhook-status, authorization, balance,
history, and Telegram behavior checks. Purchases confirmed after rollback use
the earning policy compiled into the restored Worker version.
