# V2.0.5 release guide

V2.0.5 adds centrally selectable flat and bracketed purchase earning modes.
The checked-in release uses `mode: "bracketed"` with point-floor protection
enabled. The alternative flat mode remains available and preserves BDT 50 = 1
point for all positive whole-BDT purchases.

V2.0.5 also includes the tokenized Back-navigation work and the customer-search
presentation update. Record Purchase now uses `🛍️`; both number-entry panels
repeat the selected operation; and applicable customer-search screens use the
compact `⬅️ Back` label.

## Customer-search presentation

After the administrator chooses `Search by Last Digits`, the panel shows:

```text
Selected Operation: {emoji} {operation}

Enter the last 4 or 5 digits of the WhatsApp No.
Telegram / WhatsApp Username are not accepted
```

After `Enter Full Number`, it shows:

```text
Selected Operation: {emoji} {operation}

Enter the full WhatsApp number.
Spaces and hyphens are accepted.
```

The operation label and emoji are derived from the active workflow. Back keeps
that operation active, clears later collected values, rotates the state token,
and never bypasses confirmation or performs a mutation.

## Bracketed policy

Bracketed mode applies one rate to the complete purchase amount:

| Whole-BDT purchase | Rate |
|---:|---:|
| 1-2,000 | BDT 50 = 1 point |
| 2,001-4,000 | BDT 60 = 1 point |
| 4,001-6,000 | BDT 70 = 1 point |
| 6,001-25,000 | BDT 80 = 1 point |
| 25,001 and above | BDT 100 = 1 point |

This is not progressive. Decimal purchase amounts remain invalid. Regardless
of mode, earned points are calculated with integer arithmetic and rounded
half-up once to four decimal places before storage; Telegram continues to show
two decimal places.

`pointFloorProtection: true` prevents points from dropping after a boundary by
holding the recursively protected preceding maximum until the new rate catches
up. `false` uses the raw selected bracket rate and permits the boundary drop.

## Data and migration scope

No D1 schema migration, backfill, or historical recalculation is required.
Existing customer balances, transactions, reward snapshots, mutation receipts,
history, exports, and leaderboard aggregates stay exactly as stored. Only
purchases confirmed under the deployed policy use that policy. Redemption
remains 4 points = BDT 1 and is unchanged.

Pending purchase confirmations contain a complete active-policy fingerprint.
A confirmation created under another mode, rate, bracket set, floor state, or
rounding policy is cleared and rejected before any mutation.

## Required validation

Before any release operation, run:

```powershell
npm.cmd run db:migrate:local
npm.cmd run check
git check-ignore -v .dev.vars
git check-ignore -v migrations/0001_initial_schema.sql
git status --short
```

Review the active `mode` and `pointFloorProtection` values deliberately. Test
whole-BDT input, decimal rejection, every bracket boundary in an isolated
environment, stale confirmation rejection, authorization, purchase history,
balance, leaderboard increments, and unchanged redemption behavior.

This build step does not create a branch, commit, tag, push, GitHub release,
Cloudflare deployment, webhook change, remote D1 operation, or secret change.
