# V2.0.6 release guide

V2.0.6 changes the customer identity schema. Existing WhatsApp phone customers
keep the same `customers.id`, phone, point balance, reward value, timestamps,
transactions, mutation receipts, and leaderboard aggregates. The release adds
optional WhatsApp and Telegram username aliases and makes the phone alias
optional, while requiring at least one current identifier.

This work did not apply a production migration, deploy a Worker, register a
webhook, update Telegram commands, or access production secrets. Perform every
remote step below manually in a reviewed maintenance window.

## Non-negotiable deployment order

1. Validate the exact release locally.
2. Export and protect the complete production D1 database.
3. Record pre-migration integrity totals.
4. Apply migration `0007_multi_identifier_customers.sql` remotely.
5. Verify schema, row totals, value totals, and foreign keys.
6. Deploy the matching V2.0.6 Worker.
7. Register the updated Telegram command list and run acceptance tests.

Never deploy V2.0.6 before migration `0007` succeeds. Never run the V2.0.5
Worker against the V2.0.6 conversation-state schema. Do not edit migration
`0007` after it has been deployed anywhere shared.

## 1. Local release validation

From the repository root in Windows PowerShell:

```powershell
git checkout v2.0.6
npm.cmd ci
npm.cmd run db:migrate:local
npm.cmd run check
git status --short
```

The migration and all quality gates must pass. Review the migration and the
working tree before continuing.

## 2. Authenticate and verify the target

```powershell
npx.cmd wrangler whoami
npx.cmd wrangler d1 info soulshop-rewards-db
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
```

Stop if the Cloudflare account, database name, or database ID is not the
intended production target. Migrations `0001` through `0006` must already be
applied and `0007` must be pending.

## 3. Take a protected production backup

The repository ignores SQL backups, but still store the result in protected
storage outside the repository after export.

```powershell
New-Item -ItemType Directory -Path .\backups -Force
$BackupStamp = Get-Date -Format "yyyyMMdd-HHmmss"
$BackupPath = ".\backups\soulshop-before-v2.0.6-$BackupStamp.sql"
npx.cmd wrangler d1 export soulshop-rewards-db --remote --output $BackupPath
Get-Item $BackupPath | Format-List FullName,Length,LastWriteTime
git check-ignore -v $BackupPath
```

Stop if the export fails, is empty, is not ignored by Git, or cannot be copied
to the protected backup location. Do not paste customer data into tickets,
chat, logs, or source control.

## 4. Record pre-migration integrity totals

Run and securely retain the output for comparison:

```powershell
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "PRAGMA foreign_key_check;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS customer_count, COALESCE(SUM(point_balance_units), 0) AS total_point_units, COALESCE(SUM(rounded_reward_bdt), 0) AS total_reward_bdt FROM customers;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS transaction_count, COALESCE(SUM(points_delta_units), 0) AS net_transaction_units FROM transactions;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS receipt_count FROM mutation_receipts;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS aggregate_count, COALESCE(SUM(earned_point_units), 0) AS total_aggregate_units FROM leaderboard_aggregates;"
```

`PRAGMA foreign_key_check` must return no rows before migration. Any existing
violation is a release blocker.

## 5. Apply migration 0007

Put the bot into a maintenance window so no Telegram mutation is accepted
during the schema rebuild. Then run:

```powershell
npm.cmd run db:migrate:remote
```

Confirm that only `0007_multi_identifier_customers.sql` is pending before
accepting the prompt. The migration is transactional and contains copy and
foreign-key guards; if it fails, do not deploy and do not manually mark it as
applied.

## 6. Verify the migrated database

```powershell
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "PRAGMA foreign_key_check;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT name FROM sqlite_master WHERE type = 'table' AND name LIKE '%v205%';"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS customer_count, COALESCE(SUM(point_balance_units), 0) AS total_point_units, COALESCE(SUM(rounded_reward_bdt), 0) AS total_reward_bdt, SUM(CASE WHEN whatsapp_number IS NULL AND whatsapp_username IS NULL AND telegram_username IS NULL THEN 1 ELSE 0 END) AS customers_without_identifier FROM customers;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS transaction_count, COALESCE(SUM(points_delta_units), 0) AS net_transaction_units FROM transactions;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS receipt_count FROM mutation_receipts;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS aggregate_count, COALESCE(SUM(earned_point_units), 0) AS total_aggregate_units FROM leaderboard_aggregates;"
```

Release blockers:

- any foreign-key row;
- any table name containing `v205`;
- `customers_without_identifier` other than zero;
- a changed customer count, balance sum, rounded-reward sum, transaction count
  or net unit sum, receipt count, aggregate count, or aggregate-unit sum;
- migration `0007` not listed as applied.

Do not deploy while any blocker remains. Preserve the backup and investigate.

## 7. Deploy and register the command

Only after every database check passes:

```powershell
npm.cmd run deploy
npm.cmd run telegram:set-commands
```

Webhook registration is unchanged and should not be repeated unless its URL or
secret intentionally changed.

## 8. Production acceptance

Using only the configured administrator account:

1. Find an existing phone customer and confirm its balance and history match
   the pre-release values.
2. Add a WhatsApp username, search it with different capitalization, and
   confirm display preserves the entered capitalization.
3. Add a Telegram username and confirm the customer is reachable through the
   phone and both usernames.
4. Change the WhatsApp phone and verify both the new phone and usernames reach
   the same customer ID, balance, and history; the old phone must not match.
5. Reject an invalid username and a same-platform duplicate without merging or
   changing either customer.
6. Remove one alias while another remains and verify final-alias removal is
   blocked.
7. Record a small reviewed test purchase and confirm the normal atomic reward
   path remains intact.
8. Confirm customer and transaction CSV files contain both username columns.

## Rollback and recovery

There is no in-place down migration. If `0007` fails, leave the old Worker in
place and investigate; D1 should roll back the failed migration transaction.

If `0007` succeeds but production must return to V2.0.5, do not deploy the old
Worker against the new schema. Create a separate D1 database, import the
protected pre-V2.0.6 SQL export into that database, verify counts and foreign
keys, update the Worker binding to the restored database, and deploy the
matching V2.0.5 Worker in one reviewed recovery operation. Keep the migrated
database untouched until recovery is confirmed.

Never delete or overwrite the only production database or the only backup as a
rollback shortcut.
