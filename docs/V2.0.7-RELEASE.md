# V2.0.7 release guide

V2.0.7 upgrades a V2.0.6 database by loosening only the WhatsApp username
constraint to permit valid periods. Existing customer IDs, identifiers,
capitalization, balances, timestamps, transactions, mutation receipts,
leaderboards, processed updates, and conversation state must remain unchanged.
Telegram username constraints and per-platform case-insensitive uniqueness
remain in force.

The V2.0.7 Worker also fixes valid photos and other non-text Telegram messages
being rejected as malformed webhook requests. Media and captions are not used
as workflow input or stored; the current workflow remains unchanged, and the
valid update is acknowledged with HTTP `200` even if its one informational
response cannot be delivered. This Worker-only fix adds no migration and does
not modify migration 0008.

This repository work does not apply a production migration, deploy a Worker,
register a webhook, update Telegram commands, or access production secrets.
Perform every remote step below manually in a reviewed maintenance window.

## Non-negotiable deployment order

1. Validate the exact V2.0.7 release locally.
2. Export and protect the complete production D1 database.
3. Record pre-migration integrity totals.
4. Confirm migrations through `0007_platform_identity_constraints.sql` are applied
   and only `0008_allow_whatsapp_username_period.sql` is pending.
5. Apply migration 0008 remotely during a maintenance window.
6. Verify row totals, value totals, identifiers, and foreign keys.
7. Deploy the matching V2.0.7 Worker and run administrator acceptance tests.

Never deploy V2.0.7 before migration 0008 succeeds. Do not edit migration 0007
or any other previously deployed migration.

## 1. Local release validation

From the repository root in Windows PowerShell:

```powershell
git checkout v2.0.7
npm.cmd ci
npm.cmd run db:migrate:local
npm.cmd run check
git status --short
```

Review migration 0008 and the complete diff before continuing.

## 2. Authenticate and verify the target

```powershell
npx.cmd wrangler whoami
npx.cmd wrangler d1 info soulshop-rewards-db
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
```

Stop if the Cloudflare account, database name, or database ID is not the
intended production target. Migrations 0001 through 0007 must already be
applied and 0008 must be pending.

## 3. Take a protected production backup

```powershell
New-Item -ItemType Directory -Path .\backups -Force
$BackupStamp = Get-Date -Format "yyyyMMdd-HHmmss"
$BackupPath = ".\backups\soulshop-before-v2.0.7-$BackupStamp.sql"
npx.cmd wrangler d1 export soulshop-rewards-db --remote --output $BackupPath
Get-Item $BackupPath | Format-List FullName,Length,LastWriteTime
git check-ignore -v $BackupPath
```

Stop if the export fails, is empty, is not ignored by Git, or cannot be copied
to protected storage outside the repository. Never paste customer data into
chat, tickets, logs, tests, or source control.

## 4. Record pre-migration integrity totals

Run and securely retain the output:

```powershell
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "PRAGMA foreign_key_check;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS customer_count, COALESCE(SUM(point_balance_units), 0) AS total_point_units, COALESCE(SUM(rounded_reward_bdt), 0) AS total_reward_bdt FROM customers;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS transaction_count, COALESCE(SUM(points_delta_units), 0) AS net_transaction_units FROM transactions;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS receipt_count FROM mutation_receipts;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS aggregate_count, COALESCE(SUM(earned_point_units), 0) AS total_aggregate_units FROM leaderboard_aggregates;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS state_count FROM conversation_states;"
```

`PRAGMA foreign_key_check` must return no rows before migration. Any violation
is a release blocker.

## 5. Apply migration 0008

Pause bot mutations for the dependency-aware table rebuild, verify only 0008
is pending, then run:

```powershell
npm.cmd run db:migrate:remote
```

The migration copies all customer columns, rebuilds every direct
customer-dependent table, recreates indexes, and runs copy and foreign-key
guards. If it fails, do not deploy and do not manually mark it as applied.

## 6. Verify the migrated database

```powershell
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "PRAGMA foreign_key_check;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT name FROM sqlite_master WHERE type = 'table' AND (name LIKE '%v206%' OR name LIKE '_v207_%');"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS customer_count, COALESCE(SUM(point_balance_units), 0) AS total_point_units, COALESCE(SUM(rounded_reward_bdt), 0) AS total_reward_bdt, SUM(CASE WHEN whatsapp_number IS NULL AND whatsapp_username IS NULL AND telegram_username IS NULL THEN 1 ELSE 0 END) AS customers_without_identifier FROM customers;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS transaction_count, COALESCE(SUM(points_delta_units), 0) AS net_transaction_units FROM transactions;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS receipt_count FROM mutation_receipts;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS aggregate_count, COALESCE(SUM(earned_point_units), 0) AS total_aggregate_units FROM leaderboard_aggregates;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command "SELECT COUNT(*) AS state_count FROM conversation_states;"
```

Release blockers include any foreign-key row, leftover migration table,
customer without an identifier, changed recorded total, or migration 0008 not
listed as applied. Compare sensitive identifier samples only through protected
administrative tooling; do not print or copy production identifiers into an
untrusted log.

## 7. Deploy and accept

Only after all database checks pass:

```powershell
npm.cmd run deploy
```

Webhook and command registration are unchanged and should not be repeated
unless intentionally modified. Using only the configured administrator:

1. Find existing customers through every stored identifier and verify their
   balance and history.
2. Add and search a WhatsApp username containing a valid period; capitalization
   must remain visible and case-only duplicates must be rejected.
3. Reject leading, trailing, and consecutive WhatsApp periods, and reject every
   Telegram username containing a period.
4. Paste a fictional username wrapped in recognized bidirectional formatting
   controls and confirm it succeeds; then verify invalid input followed by a
   valid retry works without `/restart`.
5. Confirm full customer messages conditionally show WhatsApp number, WhatsApp
   username, and Telegram username in that order, with no empty line or
   `Not provided` placeholder.
6. Confirm all three standardized identifier prompts and normal Back/Cancel
   navigation.
7. Record one reviewed test purchase and verify normal reward, history,
   receipt, and leaderboard behavior remains intact.
8. During an active identifier or amount prompt, send a fictional image with a
   `/cancel` caption. Confirm the informational response appears, the operation
   and collected state are unchanged, and the expected text works immediately.
9. Repeat the non-text check with Telegram delivery temporarily unavailable in
   a controlled non-production environment. Confirm the webhook still returns
   HTTP `200`, logs contain no caption or media metadata, and no second send is
   attempted.

## Rollback and recovery

There is no in-place down migration. If 0008 fails, keep the V2.0.6 Worker in
place and investigate the rolled-back migration.

If 0008 succeeds but production must return to V2.0.6, do not run the old
Worker against the V2.0.7 schema. Create a separate D1 database, import the
protected pre-V2.0.7 export, verify counts and foreign keys, update the Worker
binding to the restored database, and deploy the matching V2.0.6 Worker in one
reviewed recovery operation. Never overwrite the only production database or
the only backup as a rollback shortcut.
