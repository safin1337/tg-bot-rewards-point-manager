# V2.0.8 release guide

V2.0.8 is a presentation-only upgrade from V2.0.7. It adds compact
identity-aware leaderboard rows, WhatsApp-ready bold receipt headings and
quoted closing taglines, WhatsApp-monospace purchase details, concise
reward-balance labels, and Bangladeshi purchase-amount grouping. It does not
change customer identifiers,
balances, reward calculations, transactions, receipts, leaderboards, workflow
state, exports, or D1 schema.

No new migration is included. The target database must already have migrations
through `0008_allow_whatsapp_username_period.sql` applied before the V2.0.8
Worker is deployed. Do not rerun or edit any previously deployed migration.

This repository work does not deploy a Worker, operate on remote D1, register a
webhook, update Telegram commands, change secrets, commit, push, or create a
tag. Perform production actions manually after review.

## Release order

1. Validate the exact V2.0.8 source locally.
2. Confirm the intended Cloudflare account, Worker, and D1 database.
3. Verify migrations through `0008` are already applied remotely.
4. Deploy the matching V2.0.8 Worker without running a remote migration.
5. Complete administrator acceptance tests.
6. Push the `v2.0.8` tag only after acceptance succeeds.

## 1. Local validation

From the repository root in Windows PowerShell:

```powershell
git switch main
git pull --ff-only
git status --short
git rev-parse HEAD
npm.cmd ci
npm.cmd run db:migrate:local
npm.cmd run check
git status --short
```

Review the complete diff from V2.0.7 and confirm that no migration `0009` was
added. Record the validated commit ID and deploy that exact commit.

## 2. Verify the production target

```powershell
npx.cmd wrangler whoami
npx.cmd wrangler d1 info soulshop-rewards-db
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
```

Stop if the account, database name, or database ID is unexpected, or if any
migration through `0008` is pending. V2.0.8 requires no remote D1 migration.

## 3. Deploy

Only after local validation and remote migration verification:

```powershell
npm.cmd run deploy
```

Webhook and command registration are unchanged and must not be repeated unless
they were intentionally modified outside this release.

## 4. Administrator acceptance

Using only fictional or approved customer data:

1. Open current and retained weekly and monthly leaderboards.
2. Verify phone-only, WhatsApp-username-only, and Telegram-username-only entries
   use one line with the exact `WA` and `TG` labels.
3. Verify a customer with two identifiers shows `(+1 alias)` beside `pts`, and
   a customer with all three shows `(+2 aliases)`.
4. Confirm identity priority remains WhatsApp number, WhatsApp username, then
   Telegram username, and ranking order and point totals are unchanged.
5. Record reviewed purchases that display `BDT 10,201.00` and
   `BDT 1,10,201.00` in confirmation, success, latest-earning context, and
   history while retaining whole-number D1 values.
6. Confirm purchase, manual-add, redemption, and balance messages start with
   `*🏆 SoulShop Rewards Point System*`, display each closing tagline with a
   literal `> ` prefix, and produce a bold heading plus blockquotes when copied
   into WhatsApp.
7. Confirm the purchase receipt uses plain `✅ Purchase Successfully Recorded`,
   independently backtick-wrapped customer and transaction detail lines,
   `*🎉 Congratulations!*`, and the exact adjacent lines
   `Updated reward balance: {points} points` and
   `Estimated reward value: *BDT {value}*`.
8. Confirm manual-add and balance messages retain the adjacent lines
   `Current reward balance: {points} points` and
   `Estimated reward value: BDT {value}`.
9. Confirm history still omits closing taglines and CSV exports retain their
   existing numerical values.
10. Recheck balance, redemption, transaction history, and leaderboard totals to
   ensure presentation did not change persisted data.

## 5. Tag the accepted commit

After production acceptance succeeds, verify that `HEAD` is still the exact
validated and deployed commit, then create and push the release tag:

```powershell
git status --short
git log -1 --oneline
git tag -a v2.0.8 -m "Release V2.0.8"
git push origin v2.0.8
```

Stop if the worktree is not clean or the commit differs from the one recorded
during local validation. Never move the existing `v2.0.7` tag.

## Rollback

V2.0.8 adds no schema or data migration. If presentation acceptance fails,
deploy the exact V2.0.7 Worker again. Do not restore or rewrite D1 because this
release performs no database transformation. Investigate the display failure
with sanitized logs, correct it in a new reviewed commit, and rerun validation
before redeployment.
