# V2.0.9 release guide

V2.0.9 upgrades the welcome-only dashboard into a business summary, adds
configurable per-customer test accounts, and stores a cumulative lifetime
redemption summary while retaining only its newest 40 global snapshots.

This release requires migration `0009_dashboard_and_test_accounts.sql` before
the V2.0.9 Worker is deployed. The migration preserves existing balances and
history, defaults every existing account to normal, and intentionally starts
the lifetime redemption table empty. No production action is automated.

## 1. Safety boundary

Run production commands only from the reviewed V2.0.9 commit. Do not deploy the
new Worker before migration 0009 succeeds: the Worker expects `customers.is_test`
and `lifetime_redemption_snapshots` to exist.

Before the maintenance window:

1. Confirm all pre-V2.0.9 redemptions belong only to disposable test accounts.
2. Record the three test accounts by a safe identifier; do not place those
   identifiers in source, documentation, logs, or screenshots.
3. Pause administrator mutations.
4. Take and protect a full remote D1 export.
5. Verify migrations through 0008 are already applied and only 0009 is pending.

## 2. Local validation

From PowerShell in the repository root:

```powershell
npm.cmd ci
npm.cmd run db:migrate:local
npm.cmd run check
git diff --check
git status --short
```

Review the complete diff and migration. The build command inside `check` is a
Wrangler dry run; it does not deploy.

## 3. Protected backup

Authenticate to the intended Cloudflare account manually, resolve the exact
database, then export it to an ignored private directory:

```powershell
npx.cmd wrangler whoami
npx.cmd wrangler d1 info soulshop-rewards-db
New-Item -ItemType Directory -Force "backups" | Out-Null
npx.cmd wrangler d1 export soulshop-rewards-db `
  --remote `
  --output="backups/soulshop-pre-v2.0.9-YYYY-MM-DD.sql"
```

Do not continue until the export exists, is non-empty, and is stored securely.

## 4. Pre-migration evidence

Capture aggregate values without exporting private identifiers into shared
logs:

```powershell
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command="SELECT COUNT(*) AS customers, COALESCE(SUM(point_balance_units), 0) AS point_units, COALESCE(SUM(rounded_reward_bdt), 0) AS stored_rounded_bdt FROM customers;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command="SELECT COUNT(*) AS transactions FROM transactions;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command="SELECT COUNT(*) AS receipts FROM mutation_receipts;"
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
```

`stored_rounded_bdt` is evidence only; the new dashboard correctly recalculates
one estimated value from combined point units instead of summing stored rounded
customer values.

## 5. Apply migration 0009

During the paused mutation window:

```powershell
npm.cmd run db:migrate:remote
```

Verify immediately:

```powershell
npx.cmd wrangler d1 migrations list soulshop-rewards-db --remote
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command="PRAGMA foreign_key_check;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command="SELECT COUNT(*) AS customers, COALESCE(SUM(point_balance_units), 0) AS point_units, SUM(CASE WHEN is_test = 0 THEN 1 ELSE 0 END) AS normal_accounts, SUM(CASE WHEN is_test = 1 THEN 1 ELSE 0 END) AS test_accounts FROM customers;"
npx.cmd wrangler d1 execute soulshop-rewards-db --remote --command="SELECT COUNT(*) AS lifetime_rows FROM lifetime_redemption_snapshots;"
```

Release blockers are: any foreign-key row, changed customer or point-unit
totals, a nonzero test-account count before classification, a nonempty lifetime
table, or a migration status other than successfully applied.

## 6. Deploy the matching Worker

Only after the schema checks pass:

```powershell
npm.cmd run deploy
```

Verify the returned Worker URL and health endpoint, then resume administrator
access only for the acceptance steps below.

## 7. Classify the existing test accounts

Using only the authorized administrator:

1. Open `/tools` and choose `Manage Test Accounts`.
2. Find each of the three known test accounts through normal customer search.
3. Review the identifiers, choose `Mark as Test Account`, and confirm.
4. Verify `🧪 Test Account` appears and the account disappears from dashboard
   and leaderboard totals under the default configuration.
5. Do not convert an account to normal unless its exact balance is zero and it
   is genuinely ready to become a real customer account.

This action preserves each test balance and retained history. It removes
retained leaderboard aggregates under the default exclusion. Existing test
redemptions remain visible in history but do not enter the new lifetime total.

## 8. Acceptance

Verify:

- `/start` shows the expected included customer count and combined point/BDT
  totals, with lifetime redemptions initially zero.
- The main and More Tools keyboards match the documented layouts.
- A future test-account redemption changes its balance/history but not the
  lifetime business totals.
- A future normal-customer redemption increments the lifetime count and point
  total exactly once, including after a repeated callback/update.
- Both CSV exports include `account_type` and retain exact point precision.
- Test accounts do not rank; normal accounts still rank and mutate normally.
- Conversion with a nonzero test balance is rejected. After `Redeem All Points`
  reaches exact zero, conversion confirmation succeeds.

After acceptance, command registration may be updated explicitly:

```powershell
$env:BOT_TOKEN = "YOUR_BOT_TOKEN_IN_THIS_PROCESS_ONLY"
npm.cmd run telegram:set-commands
Remove-Item Env:BOT_TOKEN
```

The code keeps older direct commands routable even though the registered menu
is shorter.

## 9. Tag only after production acceptance

```powershell
git tag -a v2.0.9 -m "Release V2.0.9"
git push origin v2.0.9
```

Do not tag merely because local checks passed.

## 10. Rollback

Migration 0009 has no in-place down migration. Its customer column and summary
table are additive, so the V2.0.8 Worker can operate on the migrated database.
Before rolling the Worker back, clear any active `MANAGE_TEST_ACCOUNT`
conversation state so the older Worker never reads an unknown operation.

Do not delete `is_test`, lifetime snapshots, balances, or history manually.
Preserve the backup and investigate first. If restoring the pre-release backup
is genuinely required, restore it into an isolated recovery database, verify
it, and obtain explicit approval before changing production bindings.

## Release-state note

Preparing this file, migration, tests, and source does not apply a remote
migration, deploy a Worker, register Telegram commands, change a webhook,
create a commit, push, or tag. Each external step above remains manual.
