# V2.1.0 Release Guide

Release name: **Telegram Bot: Loyalty Rewards Point Manager V2.1.0**.
The configurable in-bot branding remains independent of the release name.

V2.1.0 adds customer merging and splitting within Manage Customer Identities.
The selected customer ID survives; exact balances combine, retained history
and receipts move together, and leaderboard earnings combine within matching
periods and reset generations. It requires migration
`0010_customer_merges.sql` and `0011_customer_splits.sql`. Splitting separates
all current identities into zero-point accounts and clears leaderboard earnings.
Both confirmation screens explain the reset policy. Detailed behavior is in
[Customer Merging](CUSTOMER-MERGING.md).

## Local Validation

```powershell
npm.cmd ci
npm.cmd run db:migrate:local
npm.cmd run check
git diff --check
git check-ignore -v .dev.vars
git check-ignore -v migrations/0001_initial_schema.sql
git status --short
```

Review the version changes in both package manifests, migration 0010, merge
implementation, split migration 0011, tests, and documentation. The build is a deployment dry run.
An exit code of 1 with no output for the migration ignore check means the
tracked migration is not ignored.

## Production Upgrade

These external steps require separate administrator authorization. Preparation
of this release does not run them.

1. Confirm the intended Cloudflare account, Worker, and D1 database. Pause
   administrator mutations during the upgrade and cancel pending workflows.
2. Take and protect a full D1 backup. Record business totals and retained
   transaction/receipt counts without exposing identifiers.
3. Apply all pending migrations, including 0010 and 0011, before deploying the Worker:

```powershell
npm.cmd run db:migrate:remote
```

4. Verify existing business rows and balances are unchanged,
   both new receipt tables are empty on their initial upgrade, and
   `PRAGMA foreign_key_check;` returns no rows.
5. Deploy the reviewed V2.1.0 Worker:

```powershell
npm.cmd run deploy
```

6. Verify `/health` and run the acceptance checks below. Telegram's command
   list, webhook, and secrets need no change for this release.

## Acceptance Checks

- Merge confirmation warns that a later split starts all accounts at zero.
  Split confirmation shows points to erase. Back/Cancel preserve data; confirming
  creates one zero-point account per identity and clears leaderboard earnings.
  History remains on the original ID and lifetime redemption totals stay intact.

- Two controlled compatible accounts with 100 and 200 points show a
  300-point preview. Back and Cancel leave both accounts intact.
- Confirm Merge leaves one selected customer ID with 300 points and all
  original identifiers. Conflicting identities and mixed test/normal accounts
  are rejected without writes.
- Phone, suffix, WhatsApp username, and Telegram username searches find the
  combined account. Quick Buy and normal purchase assign new points once.
- Normal redemption and Redeem All use the combined exact balance and require
  confirmation. Leaderboard earnings remain unchanged by redemption.
- History and exports contain the combined newest 40 transactions, retaining
  original timestamps and balance snapshots. Corresponding receipts remain
  bounded to those transactions.
- Weekly/monthly leaderboards combine eligible earnings by their original
  period and reset generation. Old earnings never enter the current period.
- Later identity edits still work. Dashboard point totals and lifetime
  redemption snapshots stay unchanged by the merge; customer count decreases.

Concurrent confirmations, rollback, delayed updates, and delivery retries are
covered by the local Workers tests; do not fabricate production updates.

## Tagging and Rollback

After reviewing and committing the release, and after production acceptance:

```powershell
git tag -a v2.1.0 -m "Release V2.1.0"
git push origin v2.1.0
```

Migrations 0010 and 0011 are additive and the previous V2.0.10 Worker can run with them.
Cancel pending merge workflows before reverting Worker code, because V2.0.10
does not recognize `CONFIRM_CUSTOMER_MERGE` or `CONFIRM_CUSTOMER_SPLIT`. Preserve migration records and
merge receipts. Reverting code does not undo completed merges; reversal
requires reviewed restoration of customer data and all dependencies from a
protected backup. Do not manually recreate absorbed accounts or subtract points.

## Release State

Versioning this release does not create a Git commit/tag, push, apply a remote
migration, deploy a Worker, register Telegram commands, or change webhooks or
secrets. Local verification is recorded in
[Customer Merging](CUSTOMER-MERGING.md#split-verification-2026-10-09).
